A set of Hermes agent profiles that can research, design, build and verify your websites and apps at the quality bar your existing portfolio already sets. Grounded in what the running instance actually is, not what it could be.

The thesis in one paragraph

Hermes runs on a Linux container that cannot see your Windows drive, so git is the bridge. It reads every repo's CLAUDE.md automatically, which means your per-project rules transfer for free. Its skill format is identical to the one your 32 skills already use, so those transfer for free too. What has to be designed is the division of labour between agents, the gate that stops bad work shipping, and which model does what.

What stays behind, for now

MegaBonk permanently: Unity's editor cannot run usefully here, and pretending otherwise would waste weeks. Rise and Job-tracker temporarily: the container does not have the disk or memory for the Android and Flutter toolchains until it is resized. See page 3. Websites move immediately.

How to use this

Pages 1 to 4 are what is true today, including decisions already made. Pages 5 to 10 are the design and the reasoning behind it. Page 11 is the ordered build sequence with checkboxes that remember your progress. This document gets updated as we answer things, so it stays the single source rather than something to redo.

The split

Websites-only for now. The Android and Flutter toolchains would exhaust 14.8 GiB during installation, and a Gradle daemon wants 1.5 to 2 GB heap on its own, which on a 4 GiB box also running the agent means swapping rather than building.

Resize target, when apps join

Roughly 4 vCPU, 8 to 12 GiB RAM, 80 GiB disk. On Proxmox the disk can grow online; cores and memory need a short restart. This is step 9, not now, and it depends on what the Homelab node has spare.

Why this is fine

Phase one is websites, and websites fit comfortably. Nothing about the current sizing blocks steps 1 through 8. Resizing before proving the pipeline works would be spending resources on an unvalidated design.

Design / 05

Roles are profiles

The intuitive design does not work on this platform. Here is the constraint that forces the real one.

What everyone tries first

One subagent per co-worker: a researcher, a designer, a builder, spawned by a manager agent. It maps cleanly onto how you described it, and it is wrong here.

The blocking constraint

Children spawned by delegate_task inherit the parent's enabled toolsets, specifically so a model cannot grant a child capabilities the parent lacks. They also cannot be handed their own skills per call. A "designer" child would carry the builder's full toolset and the builder's expensive model.

What actually isolates

Profiles. Each Hermes profile is a separate instance with its own config, model, tool set, skills, memory, sessions and gateway process. That is exactly the boundary a specialist role needs.

ConcernMechanismWhy
Role specialisationProfileOnly thing that isolates model, tools and skills together.
Domain knowledgeThe repo's CLAUDE.mdAuto-injected. Kotlin vs Flutter vs vanilla needs no config.
Parallelism inside a roledelegate_taskFan out to 3 children on a cheap model, only summaries return.
Hand-off between roleshermes kanbanBuilt-in multi-profile assign and dispatch.
The consequence worth noticing

Domain expertise costs nothing to move. Because Hermes reads each repo's CLAUDE.md into the prompt automatically, an agent working in the Rise repo already knows the Rise rules. You wrote that documentation for yourself, and it turns out to be the configuration.

Why phase it

Building all five before any of them has run a real job means guessing at the interfaces between them. Three profiles produce work you can judge, and judge safely. Judge it, then specialise.

Why forge cannot close its own work

Two of the three phase-one profiles exist to say no. That ratio is deliberate: the builder is the part a model is already good at, and the reviewing is the part that disappears when you remove the human.

Design / 07

The quality gate

This is the page that decides whether the output matches your existing portfolio, so it is worth being blunt about where the risk actually sits.

Where your current quality comes from

Not the model alone. Five things: the skills, the per-project CLAUDE.md, a strong model, mandatory Playwright QA, and you reviewing the result. The first three move to Hermes cleanly. The fourth is already written down as a rule. The fifth is exactly what automation deletes.

The real risk

Automating the pipeline removes the reviewer, not the builder. If nothing replaces you at that step, quality regresses quietly and you find out weeks later on a live client site. warden exists to be that replacement, which is why it holds reject authority rather than being advisory.

The gate, concretely

  1. forge finishes and moves the kanban task to "needs review". It cannot close its own work.
  2. warden pulls the branch and builds it in a clean checkout.
  3. Playwright run. Desktop and mobile widths, both themes, cache busted. This mirrors the QA rule you already made mandatory for UI work.
  4. aegis reviews the same diff in parallel. Both gates must pass. Detail on page 8.
  5. Pass posts the diff, the screenshots and the security verdict to the project channel for a human yes.
  6. Fail from either gate reopens the task with the evidence attached, assigned back to forge.
Deliberately not automated

Nothing merges or deploys off warden alone. The final yes stays human until this pipeline has a track record you actually trust. That is a decision to revisit in a few months, not a permanent rule.

Design / 08

aegis

A dedicated security profile with authority to block a merge. The hard part is not the reviewing, it is making its advisory feed relevant enough that you keep reading it.

Four standing jobs

Diff review

Blocking

Runs the security-review skill against every branch before merge. Injection paths, auth and authorisation, unsafe deserialisation, HTML injection, dangerous shell construction.

Secret scanning

Blocking

ghost-scan-secrets on every diff. Nothing containing a key, token or credential merges. This is the one gate with zero tolerance and no judgement call.

Dependency advisories

Daily cron

Cross-references live advisories against your actual lockfiles. Filing method below, and it is the part that decides whether this is useful or noise.

Standing audit

Weekly cron

owasp-security-check across the deployed sites. Headers, cookie flags, exposed endpoints, TLS, form handling.

How it stays relevant

You said you do not want Intune and Microsoft advisories. The wrong way to solve that is a keyword blocklist, which will silently drop something that mattered. The right way is to make relevance structural.

The filter rule

An advisory is reported only if the affected package actually appears in one of your dependency manifests. The cron job reads every package-lock.json, pubspec.lock, composer.lock and Gradle lockfile under projects/, then matches advisories from the GitHub Advisory Database scoped to those ecosystems. Windows Server and Intune CVEs never match anything you own, so they never appear. Not filtered out, simply never matched.

The manual watchlist

Some things you run have no lockfile, so they need naming explicitly. This list is the whole scope, and anything outside it is not aegis's business:

TargetSourceWhy it is on the list
WordPress core and pluginsPatchstack, WordfenceContact Form 7, Yoast, UpdraftPlus, FileBird, Really Simple SSL, Easy WP SMTP and the rest on the live site.
Payload CMSGitHub releasesRuns the Van den Dam client site.
Supabase and PostgresVendor advisoriesSelf-hosted instance plus RLS as the actual security boundary.

Where your actual risk is

Not in the Next.js code. It is the WordPress site. Vulnerable WP plugins are the most routinely exploited thing in a portfolio shaped like yours, they are exploited by automated scanners within days of disclosure, and that site is run by people who will not be reading advisories. If aegis only ever did one job well, this would be the one.

What it deliberately cannot do

  • No git write access. It reports and blocks, it does not patch. An agent that both finds and silently fixes security issues is a bad idea, and a patch needs review like any other change. Not enforced today: every profile runs as the same hermes user and shares one SSH key, so this is currently a statement of intent, not a control. Enforcing it needs either a separate OS user for aegis or branch protection doing the work at GitHub.
  • It files, it does not fix. A confirmed advisory becomes a kanban task for forge, which then goes through both gates like everything else.
  • No deploy credentials, same as every other profile.

Models and cost

You want Opus 5 on your subscription rather than per-token. That is possible, and it collides with the rest of what you want in a way worth understanding before you build on it.

The allocation

ProfileTierReason

aegisHighSecurity reasoning degrades fastest on a weak model. Do not economise here either.
scoutFreeSummarising search results. Your Nemotron is genuinely fine.

delegation.modelCheapGlobal setting. Fan-out must not burn top-tier tokens.

Opus 5 on the subscription

Hermes docs state it prefers refreshable Claude Code credentials over copied env tokens, and accepts CLAUDE_CODE_OAUTH_TOKEN. So it can ride Claude Code credentials, which on a Max plan are subscription-backed rather than metered.

Warning one, policy

Those credentials are issued for Claude Code. Feeding them to a different agent framework is not what the subscription terms are written around. It may work, it may get throttled, the token may be invalidated. Do not make it the only path.

Warning two, arithmetic

This is the bigger one. "No tokens" and "everything automated" pull against each other. A subscription is rate-limited for one human working interactively. You are describing five profiles, three concurrent children each, plus daily and weekly security cron jobs. That is precisely the shape of load a subscription throttles hardest, and it will fail at night with nobody watching.

The practical resolution: put forge on Claude Code credentials, configure hermes fallback to OpenRouter underneath it, and keep the cheap tier for delegation. An unattended run then degrades to a slower model instead of dying at 3am. Also bump your Mixture of Agents preset, it still points at claude-opus-4.8.

Design / 10

Talking to the agents

You asked what Buzz adds when Hermes already has agents. They are different layers, and for now you only need one of them.

Buzz and Hermes are not competitors

Hermes

The worker

Runs the agent loop, holds the tools, calls the model, edits files, drives the terminal. It does the work.

Buzz

The office

Chat, channels, threads, git repos, canvases, audit log. It runs no agents at all. It is agent-agnostic and hosts whatever harness you plug in.

The bees are not a rival workforce. A bee is whatever harness you connect, and Hermes would be the bee. Buzz is where you and the bee talk, and where the bee's work is recorded.

What Buzz would add

  • Cryptographic agent identity. Each agent signs its own work with its own keys. Once four profiles are committing, provable attribution stops being academic.
  • Git in the same place as the conversation. Agents open repos, send patches and review in-channel instead of round-tripping through GitHub.
  • One channel per project, which is the structure this plan already assumes.
  • Self-sovereign. Your own relay, your data. Apache 2.0, self-hostable.
Recommendation

Use Telegram now, not Buzz. It is in the channel list with QR setup, Hermes creates the bot for you, it takes about five minutes, and it works from your phone. Buzz is at v0.4.21 with unfinished mobile clients, and its value is agent identity and audit trails across many agents. You have one agent and one human. Revisit it at step 9, by which point Buzz will have had months to settle.

If you want self-hosted chat that is boring and works today, Mattermost and Matrix are both mature and both already supported by Hermes. Buzz wins on being genuinely agent-native. It just is not ready to be load-bearing yet.

    A real task through forge, then both gates, then a human yes. This is the go or no-go. If the quality is not there, stop and fix it before scaling.

  • 09

Every step before 7 exists to make 7 meaningful. Jumping to the interesting parts, five profiles and Buzz and cron, gives you a large system whose output nobody has ever checked.

Execution / 12

Guardrails

Agents on this box get a terminal, git push rights and API keys, behind a dashboard exposed through your tunnel. These are the non-negotiables.

Access

  • Keep Cloudflare Access in front of the dashboard. It is what returned a 403 when I first tried to fetch the URL, which is correct behaviour. Do not loosen it to make automation easier.
  • Agents push as your main Curbi account, via an account-level SSH key. Every project repo is private, so per-repo deploy keys would mean a paste per repo forever. The scoping half of this control is therefore gone: the box can reach every repo you own. Branch-only pushes, never to main, is now the single compensating control and has to be enforced, not assumed. Enforce it at GitHub with branch protection on main, not by asking the agent nicely in a prompt.
  • Deploy credentials stay out of forge. Deployment is a separate human-triggered step until the pipeline has earned trust.

Secrets

  • Use hermes auth credential pools or the Bitwarden integration. Never a repo, never a skill, never a prompt.
  • The skills repo becomes a shared surface across two machines. It must contain no keys, ever.

Untrusted content

  • scout reads the open web and has no repo write access by design. That separation is a security boundary, not only a cost one.
  • Hermes scans hub-installed skills for prompt injection. Anything sourced outside your own skills repo gets read before it is enabled.
Where this ends up

After step 6 you will know whether this produces work you would put your name on. Everything past that is scaling something already proven. If step 6 disappoints, the honest move is to fix the gate or the model, not to add more agents.
